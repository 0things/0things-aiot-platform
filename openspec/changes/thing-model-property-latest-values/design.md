## Context

设备详情属性页已迁移为 `PropertyTab`，但其当前值来源仍需从设备影子和原始遥测接口中移除。产品 TSL 存储为 JSON，定义了属性标识符、名称、数据类型、单位和读写方式；现有时序查询接口已经能按设备和属性读取历史点。

## Goals / Non-Goals

**Goals:**

- 为设备详情提供一个按 TSL 属性定义对齐的最后值读模型。
- 使用一个批量时序查询获取所有定义属性的最后上报点，避免前端为每项属性独立请求历史接口。
- 保持历史趋势查询接口及其时间范围交互不变。

**Non-Goals:**

- 不修改产品 TSL 编辑能力或其 JSON 格式。
- 不修改设备影子能力、设备上报协议或时序点写入流程。
- 不在本变更中提供属性下发或写入能力。

## Decisions

### 新增设备范围的属性最后值端点

新增 `GET /devices/:deviceKey/thing-model/properties`，由设备资源负责鉴权与设备存在性校验。响应使用 `properties` 数组，数组顺序严格沿用 TSL `properties` 顺序。

选择专用端点而非扩展 `/devices/:deviceKey/telemetry`，因为后者是历史遗留的原始载荷读取，不能提供 TSL 元数据、缺失属性和最后上报时间。也不复用 `/shadow`，因为影子是独立的期望/上报状态模型。

### 服务端聚合定义与最后点

服务层先读取设备及其产品 TSL，解析出属性定义；再将全部属性标识符一次性提交给时序访问层查询最新点。时序结果以标识符映射回 TSL 结果，未命中的定义属性返回 `null` 值和时间。

选择服务端聚合而非前端分别请求 TSL 和每个属性历史，是为了避免 N+1 网络请求，并确保前端只展示已定义属性。批量查询在现有时序访问抽象中增加，具体存储实现可以使用原生批量查询或在存储端集中执行有限循环，但不得暴露为前端多请求。

### 前端以定义属性驱动展示与趋势选择

`PropertyTab` 使用生成的专用查询 Hook 获得属性列表。属性卡片或表格直接消费服务端返回的元数据与最后值；无最后点时显示未上报状态。趋势组件的可选属性来自该列表，选中属性后继续使用既有 `/v1/devices/:deviceKey/telemetry/history`。

选择由属性最后值端点驱动可选项，而非从任意上报 JSON 键推导，可避免未知键、缺失单位和无定义属性出现在物模型页。

### 统一物模型数据 Handler 与 Service

属性最后值与服务调用记录同属设备物模型数据区域，因此由 `ThingModelDataHandler` 暴露 `/devices/:deviceKey/thing-model/properties` 与 `/devices/:deviceKey/thing-model/service-invocations`，并由 `ThingModelDataService` 提供 `ListProperties` 与 `ListServiceInvocations` 两个查询方法。两种查询继续使用各自的数据仓储和 DTO，避免在 API 契约或数据模型层混合不相关的记录结构。

## Risks / Trade-offs

- [TSL JSON 格式无效或不存在] → 返回既有资源/校验错误，前端展示加载失败状态，不使用原始遥测回退。
- [设备定义属性较多] → 时序访问层以单次批量操作处理，并限制为 TSL 定义集合。
- [部分属性没有历史点] → 保留定义属性并显式返回空最后值，避免用户误以为属性不存在。
- [最后点查询与历史趋势查询的短暂不一致] → 两者均以时序存储为来源，允许高频上报期间的最终一致性。

## Migration Plan

1. 部署后端端点和 Swagger 契约，生成前端客户端。
2. 前端切换属性页到专用端点，并删除该页面对影子与原始遥测接口的调用。
3. 验证包含已上报、未上报和无 TSL 的设备场景；失败时可回滚前端版本，后端新增接口保持向后兼容。
